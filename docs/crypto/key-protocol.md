# enclip 鍵プロトコル仕様

この文書は、enclip が端末間でクリップボードの内容を共有するときの鍵の構成と、端末の追加、送信、受信の手順を定めます。
形式モデル `enclip.spthy` はこの文書を正本として書いており、仕様を変えたときはモデルも直して検証し直します。

## 1. 範囲

この仕様は、最小版（Windows と iPhone、クラウド経由、アカウントなし）の鍵プロトコルを対象にします。
端末の削除と鍵の作り直し、アカウントによる復旧、ユーザー間の共有、LAN 経由の通信は対象外で、追加するときに改めて仕様とモデルを足します。

## 2. 脅威モデル

### 2.1 攻撃者

サーバーと通信路は攻撃者が完全に握っているものとします。
攻撃者は、すべての通信を読み、止め、並べ替え、再送し、自分で作った値を送れます。
サーバーの運営者（enclip の開発者を含む）もこの攻撃者に含みます。

加えて、攻撃者は端末に表示された QR コードを盗み見られるものとします（撮影、画面共有、肩越しの覗き見など）。

### 2.2 保証すること

1. 送った内容は、同じグループの端末以外には読めない
2. ユーザー鍵とアイテム鍵は、同じグループの端末以外に漏れない
3. 端末が受け入れる内容は、同じグループの端末が送ったものに限られ、改ざんされたものは受け入れない
4. 端末の追加で、既存端末が受け入れるのは利用者が QR コードを読ませた端末だけで、新端末が受け取るユーザー鍵は本物に限られる
5. 端末は同じアイテムを二度受け入れず、期限切れのアイテムも受け入れない

### 2.3 保証しないこと

- 通信の妨害（サーバーが配信を止めること）は防げない。届かないことは利用者が気づける形にする
- 暗号アルゴリズムそのものの強度。形式検証では暗号は破れないものとして扱う
- 端末そのものが乗っ取られた場合。乗っ取られた端末はユーザー鍵を持つので、グループのすべての内容を読める
- OS のクリップボードに置いた後の内容。ほかのアプリが読めるので、機密の項目は一定時間後にクリップボードから消すことで影響を抑える

## 3. 鍵の構成

| 鍵 | 作る端末 | 用途 | 保存場所 |
|---|---|---|---|
| 端末鍵 | 各端末 | 端末の追加で、ユーザー鍵を受け取る。参加の承認に署名する | 端末の安全な保存領域（iOS はキーチェーン、Windows は DPAPI）。端末の外に出さない |
| ユーザー鍵 | グループを作った最初の端末 | アイテム鍵を包む | 各端末の安全な保存領域 |
| アイテム鍵 | 送る端末 | 1 件の内容を暗号化する。1 件ごとに新しく作る | 包んだ形でアイテムと一緒に送る |

グループ ID は、最初の端末がグループを作るときに乱数で作ります。
サーバーは、グループ ID、アクセス用トークンのハッシュ、暗号化されたアイテム、ペアリング中にやりとりするメッセージだけを持ちます。

端末鍵は 32 バイトの乱数 1 つで表し、HKDF で署名用の Ed25519 鍵と、ユーザー鍵を受け取るための X25519 鍵を導出します。
形式モデルでは 1 つの鍵ペアを署名と暗号化の両方に使っていますが、実装では用途ごとに鍵を分けます。

アクセス用トークンは、グループを作るときに乱数で作り、ユーザー鍵と一緒に新端末へ渡します。
サーバーは、トークンを持つ端末だけにアイテムの送信と取得を許します。
QR コードにはトークンが載らないので、QR コードを盗み見た人は、サーバーへ投稿して配信を妨げられません。
内容の秘匿と真正性は暗号が担い、トークンは安全性の保証には使いません。

## 4. 手順

### 4.1 端末の追加

既存端末を A、新しい端末を B とします。

1. A は、ペアリング ID とペアリング秘密を乱数で作り、ペアリング ID をサーバーに登録する。ペアリングは 1 台を承認した時点か、A でペアリング画面を閉じた時点で終わり、サーバーの登録も消す。時間による有効期限は設けない（A が終了を伝えられないまま残った登録は、サーバーが 1 日後に片付ける。これは保存領域の掃除で、安全性には関係しない）
2. A は、ペアリング ID、ペアリング秘密、A の公開鍵、グループ ID を QR コードで表示する
3. B は QR コードを読み、自分の端末鍵を作る。参加申請として、ペアリング ID、B の公開鍵、ペアリング秘密で計算した MAC をサーバー経由で A へ送る
4. A は MAC を検証する。正しければ、新しい乱数（承認用ノンス）を作り、ペアリング ID、受け取った公開鍵、承認用ノンスの 3 つに A の署名を付けてサーバー経由で B へ送る
5. B は、QR コードで得た A の公開鍵で署名を検証し、署名された公開鍵が自分の公開鍵と一致することを確かめる。一致しなければ確認コードを表示しない。A と B は、ペアリング秘密、B の公開鍵、承認用ノンスから 6 桁の確認コードを計算して表示する
6. 利用者が両画面の確認コードが一致することを確かめ、A で承認する
7. A は、ユーザー鍵とアクセス用トークンを B の公開鍵で暗号化し（関連データにペアリング ID とグループ ID を含める）、A の署名を付けて B へ送る
8. B は、QR コードで得た A の公開鍵で署名を検証してから、ユーザー鍵とアクセス用トークンを取り出して保存する

確認コードの計算に承認用ノンスを含めるのは、攻撃者が確認コードを総当たりで合わせるのを防ぐためです。
QR コードを盗み見た攻撃者は、自分の鍵で参加申請を送れます。
確認コードが申請の時点で決まる値だけから作られると、攻撃者は B の公開鍵を見てから、確認コードが一致する鍵を作れるまで鍵を作り直せます（6 桁なら約 100 万回で一致します）。
承認用ノンスは申請を受けた後に A が作るので、申請時点の攻撃者は確認コードを予測できません。

承認用ノンスの署名にペアリング ID と公開鍵を含めるのは、確認コードの偶然の一致を起こさせないためです。
署名がノンスだけを覆う場合、攻撃者は自分の申請に対して A が出したノンスを B へ渡せるので、B は自分の公開鍵で、A は攻撃者の公開鍵で確認コードを計算し、6 桁が偶然一致すれば利用者は攻撃者を承認してしまいます。
さらに、過去のペアリングで A が署名したノンスを使い回せるので、攻撃者はペアリング秘密を知っていれば、手元のノンスの中から B の確認コードが A の確認コードと一致するものを選べます。
署名が公開鍵を含めば、攻撃者の申請に対するノンスでは B が確認コードを表示しないので、偶然の一致が起きる場面そのものがなくなります。

### 4.2 送信

1. 送る端末は、内容、機密かどうか、送信元の端末 ID、作成時刻、期限を一つにまとめる
2. 新しいアイテム鍵とアイテム ID を乱数で作る
3. まとめた内容をアイテム鍵で暗号化する。関連データにグループ ID とアイテム ID を含める
4. アイテム鍵をユーザー鍵で暗号化する。関連データにグループ ID とアイテム ID を含める
5. グループ ID、アイテム ID、2 つの暗号文をサーバーへ送る

### 4.3 受信

1. ユーザー鍵でアイテム鍵を、アイテム鍵で内容を復号する。関連データが一致しなければ捨てる
2. 期限を過ぎたアイテムは捨てる
3. 受け入れたアイテム ID を期限まで記録し、記録にある ID のアイテムは捨てる
4. 表示順は、暗号文の中の作成時刻で決める

期限の判定と記録の削除には、端末の時計の現在時刻ではなく、これまでに観測した最も新しい時刻を使います（端末内に保存し、戻さない）。
時計が戻ると、期限後に記録を消したアイテムが再び期限内と判定され、サーバーの再送を二度受け入れてしまうためです。

履歴は全端末で共有する一覧です。
各端末は、サーバーにある期限内のアイテムを手順 1 と 2 で検証して履歴に並べ、同じアイテム ID は 1 件にまとめます。
手順 3 の記録は、届いたアイテムを新着として扱うか（Windows のクリップボードへの自動反映など）の判定に使い、履歴の表示には使いません。
サーバーが古いアイテムを送り直しても、履歴では同じ ID の項目と重なるだけで、新着としては扱われません。

### 4.4 期限による削除

サーバーは期限を過ぎたアイテムを削除します。
各端末も、期限を過ぎたアイテムを手元の一覧から消し、受け入れた ID の記録も期限後に消します。
期限は暗号文の中に入っているので、サーバーが期限を延ばしても端末は受け入れません。

## 5. 暗号アルゴリズム

| 用途 | アルゴリズム |
|---|---|
| ユーザー鍵の受け渡し（公開鍵暗号） | HPKE（RFC 9180、DHKEM(X25519, HKDF-SHA256)、AES-256-GCM） |
| 署名 | Ed25519 |
| 内容とアイテム鍵の暗号化 | AES-256-GCM |
| 参加申請の MAC、確認コードの計算 | HMAC-SHA256 |
| 乱数 | OS の暗号論的乱数 |

アイテム鍵は 1 件ごとに使い捨てるので、AES-GCM のノンスは乱数で作っても衝突の心配がありません。

## 6. 形式検証

`enclip.spthy` を Tamarin prover で検証します。
モデルは 2.2 の保証を補題として持ち、QR コードの漏えいを攻撃者の操作として含みます。

```sh
nix --extra-experimental-features 'nix-command flakes' shell nixpkgs#tamarin-prover -c \
  tamarin-prover +RTS -M3G -RTS --prove -D=APPROVAL -D=DEDUP docs/crypto/enclip.spthy
```

フラグを変えると、承認や重複検出を省いた場合や、承認用ノンスの署名が弱い場合の反例を確認できます。

- `-D=APPROVAL` を外す: QR コードを読んだ端末を確認なしで受け入れる方式。QR コードを盗み見られると攻撃者が参加できる。QR コードに短い有効期限を付けても、有効な間に盗み見られれば同じ
- `-D=WEAKSIG` を足す: 承認用ノンスの署名がノンスだけを覆う方式。確認コードの偶然の一致で攻撃者を承認しうる
- `-D=DEDUP` を外す: 受信側が同じアイテムを二度受け入れる方式。サーバーが古いアイテムを再送できる

確認コードの照合は、新端末の画面に出たコードを人が既存端末のコードと見比べる操作として表しています。
攻撃者は表示を見られますが、新端末の画面の表示は変えられません。
6 桁のコードが違う値から偶然一致する場合も、攻撃者が起こせる事象として含めています。

受信側の重複検出と期限の処理は、時刻を扱う状態機械として `replay_check.py` で全状態を探索します。

```sh
python3 -I docs/crypto/replay_check.py
```

### 6.1 検証結果

Tamarin prover 1.12.0 で、次の結果を確認しています。

| 補題 | 対応する保証 | 推奨案 | 承認なし | 署名が弱い | 重複検出なし |
|---|---|---|---|---|---|
| `device_sk_secrecy`（補助） | — | 証明 | 証明 | — | 証明 |
| `executable`（正常系が動く） | — | 到達可能 | 到達可能 | — | 到達可能 |
| `userkey_secrecy` | 2 | 証明 | 反例 | — | 証明 |
| `itemkey_secrecy` | 2 | 証明 | 反例 | — | 証明 |
| `item_secrecy` | 1 | 証明 | 反例 | — | 証明 |
| `approve_only_scanned_device` | 4 | 証明 | 反例 | 反例 | 証明 |
| `wrong_approval_needs_collision` | 4 | 証明 | 反例 | 証明 | 証明 |
| `joined_key_is_genuine` | 4 | 証明 | 証明 | — | 証明 |
| `item_injective_agreement` | 3、5 | 証明 | 反例 | — | 反例 |

「署名が弱い」の列は、関係する 2 つの補題だけを検証しています（全補題を一度に流すと 10 分で終わらないため）。

推奨案では、確認コードの偶然の一致を攻撃者が起こせるものとしても、QR コードを読んだ端末以外は承認されません。
攻撃者の申請に対する承認用ノンスでは、新端末が確認コードを表示しないためです。

承認なしの反例では、攻撃者が QR コードからペアリング秘密を得て、自分の鍵で参加申請を送り、既存端末がそれを承認します。
その結果、攻撃者がユーザー鍵を受け取り、以降のアイテムをすべて読めます。
署名が弱い場合の反例では、攻撃者が自分の申請に対するノンスを新端末へ渡し、両端末の確認コードが偶然一致したときに承認されます。
重複検出なしの反例では、サーバーが同じアイテムを再送し、受信側が二度受け入れます。

`replay_check.py` は、次の結果を返します。

| 条件 | 結果 |
|---|---|
| 時計が戻らない | 二度受け入れない |
| 時計が戻り、現在時刻で判定する | 反例: 受け入れ → 期限後に記録を削除 → 時計が戻る → 再送を受け入れ |
| 時計が戻り、観測した最も新しい時刻で判定する（4.3） | 二度受け入れない |

### 6.2 モデルの抽象化

モデルでは、端末を追加する側の端末と、送受信する端末が、グループ作成時の本物のユーザー鍵を使うものとして扱います。
参加した端末が受け取った鍵は、`joined_key_is_genuine` で本物と一致することを示します。
最初の端末は本物の鍵を持ち、本物の鍵を持つ端末が追加した端末も本物の鍵だけを受け取るので、参加の順に帰納するとすべての端末が本物の鍵を持ち、この扱いは実際の手順と同じ実行を表します。
受け取った鍵をそのまま使うモデルでは、端末が次の端末を追加する連鎖を探索がたどり続けて終わりませんでした。

同じ理由で、端末を追加する側はグループの端末に限らず、端末鍵を持つ任意の端末としています。
正規の端末にできることを増やす方向の近似なので、安全性の補題が成り立てば実際の手順でも成り立ちます。

乱数で作る値は、モデル上で乱数の型を付けています。
参加した端末が受け取るユーザー鍵は型を付けず、攻撃者が任意の値を送り付けられるものとして扱います。

Tamarin のモデルでは、重複検出を「同じ端末が同じアイテム ID を二度受け入れない」という制約として置いています。
この制約を実際の記録と期限の処理が満たすことは、`replay_check.py` で確かめています。
`replay_check.py` は、アイテム 2 件、時刻 0〜6 の範囲で全状態を探索したものです。

### 6.3 モデルが表していないこと

- 利用者が確認コードを見比べずに承認する場合
- 時間の経過。モデルの安全性の結果は、ペアリングがいつまで続くかに依存しないため、QR コードに時間の有効期限を設けていない
- 暗号の強度と実装の誤り
